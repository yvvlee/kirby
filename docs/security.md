# Security

Kirby treats the backend as the only authorization boundary. The web client
may hide unavailable actions, but every management request is authenticated and
authorized again by the server.

## Credentials

- Administrator passwords use Argon2id. Only encoded hashes are stored.
- Access tokens are short-lived JWTs with an issuer and explicit signing-key ID.
- Refresh tokens are random, stored only as hashes, rotated on use, and sent in
  `HttpOnly` cookies. Reuse revokes the session.
- Project API keys contain a public ID and one-time secret. The database stores
  a peppered digest and a short display suffix, never the original secret.
- Configuration secrets are wrapped in a redacting type. The structured logger
  also removes known credential forms from messages, attributes, and errors.

## Authorization

Environment roles are resolved by user and environment. Repository queries also
scope projects, configs, snapshots, keys, and imports to their owning
environment. Permission cache keys include the environment generation, so a
role change invalidates prior decisions without requiring a new login.

Runtime API keys are locked and verified in the database on every request. The
requested project key must match the credential's project. Published content
cache keys include environment, project, config key, and runtime version.

## Uploads

Object keys are generated by the server and encode environment and project
scope. Completion rejects malformed, traversing, or cross-scope keys. Local and
S3 storage recheck actual size and media type before returning a public URL.
Upload endpoints reject management JWTs, cookies, and project API keys.

Local storage is allowed only in single-server development mode. Shared
deployments must use S3-compatible storage.

## Rate limits

Login, refresh, and runtime API-key limits use the configured cache. Redis is
required by the deployment configuration, so counters are shared state even
though server processes are stateless. A cache error fails the request instead
of disabling the limit.

## Operational requirements

- Terminate public TLS at the ingress and forward only from configured proxy
  addresses.
- Use independent random JWT keys, API-key pepper, database credentials, Redis
  credentials, and object-storage credentials.
- Keep refresh-cookie origins exact. Do not use wildcard origins.
- Apply `deploy/schema.sql` manually. The service never migrates the database.
- Keep the pinned build and runtime images current, then run
  `scripts/security-check.sh` before release.

Security reports should use the process documented in the repository root
`SECURITY.md` once that public reporting policy is added.
